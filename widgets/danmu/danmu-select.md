# 弹幕优选

## 接口

组件保留 Forward 弹幕约定的三个模块：

- `searchDanmu`：搜索作品并生成带多源 ID 映射的路由。
- `getDetail`：获取选集，严格使用每个来源自己的 `animeId`。
- `getComments`：获取弹幕，严格使用每个来源自己的 `episodeId`。

## 默认调度

1. Alpha 与炊烟属于 `fast` 层，并发请求。
2. 搜索与自动匹配先比较媒体匹配置信度，不按完成时间决定结果。
3. `quality` 模式等待快速层请求由 Forward 原生网络层结算，再比较弹幕质量，避免完成顺序压过质量。
4. 质量判断先执行繁简转换、用户关键词屏蔽和去重。快速层无准确候选，或处理后的弹幕质量低于 `minQuality` 时，才请求 `deep` 层的 Lily。
5. Lily 没有对应的来源 ID 映射时不会拿其他来源的 ID 试探，避免跨库串片。
6. 同一准确标题存在多个电影条目时，详情阶段会核对每源最多四个候选，优先完整标题与“正片”，降权“精彩片段”“预告”“快看”等条目。

默认三个地址槽可以替换，也支持在一个地址槽中按行填写多个来源：

```text
来源名称,https://example.com/token
另一个来源，https://example.net/token
```

未知自定义地址默认归入快速层。内置 Lily 地址会被识别为深度层。

## 质量分

质量分是本地启发式指标，不读取或上传弹幕正文到 AI。当前信号包括：

- 可解析且未被用户关键词屏蔽的弹幕比例；
- 去重后的内容比例；
- “签到”“前排”“哈哈哈”“666”等低价值短内容比例；
- 弹幕在播放时间轴上的覆盖与跨度；
- 对弹幕总量做对数饱和，避免单纯以数量取胜；
- 来源画像仅占很小的平分权重。
- 超大弹幕集会按完整时间轴确定性均匀采样，质量评分最多处理 `12000` 条；默认输出上限为 `3000` 条，避免几十万条弹幕造成明显 CPU 与内存峰值。

它用于在已有结果中选择更合适的一组，不代表对弹幕内容真实性或主观好坏的绝对判断。

## 兼容策略

- `quality`：推荐，快速层动态质量优选，必要时使用深度层。
- `fallback`：按路由中的来源顺序逐个容灾，前一个来源无有效弹幕时才请求下一个。
- `merge`：合并已映射的快速层结果并确定性去重，不常态合并 Lily。

## 预算与超时

- `fastTimeout` 默认 `3500 ms`，只用于判断是否继续启动快速层后续步骤。
- `requestTimeout` 默认 `25000 ms`，只用于判断是否继续启动深度回退、转换和缓存等后续步骤。
- 已经发出的 `Widget.http` 请求由 Forward 原生网络层负责超时，脚本不会使用运行时未提供的 `setTimeout` 强行截断。
- `quality` 与 `merge` 会等待同层已经发出的请求结算；`fallback` 使用顺序容灾，避免无意义地同时请求所有备用源。
- 繁简字典优先读取同步缓存。冷缓存时后台预热，不阻塞本次弹幕返回，因此第一次转换可能保持原文，后续请求再使用已缓存字典。

超时、限流与服务失败不会被当成永久“无弹幕”写入缓存。
